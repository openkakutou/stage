# BG animation modeled as a new type; `.def` action-block parsing deferred; parallax formula pinned to the documented `start + camera*delta` convention

**Context:** Backlog item 005 asks for two computations: a parallax BG element's effective screen position from camera position and its scroll deltas, and an animated BG element's currently-visible sprite from elapsed time. `BGElement` already carries `ActionNumber` for an anim-type element, but no frame-sequence data exists anywhere in the model yet — real MUGEN/Ikemen stage files declare that sequence in a separate `[Begin Action N]` block within the same `.def` file (same syntax as `.air`), which `Parse` does not read yet (it tolerates and skips unrecognized sections). The exact meaning of `delta` also needed pinning down: MUGEN's own docs state delta is "how many pixels the background element should scroll for each pixel of camera movement," confirmed via the official Elecbyte stage docs.

**Decision:** Add two new, self-contained types — `BGAnimFrame` (`Sprite SpriteRef`, `Time int`) and `BGAnimation` (`Frames []BGAnimFrame`, `LoopStart int`) — mirroring `character`'s `air.Animation`/`air.Frame` shape, since the underlying file syntax is identical. Add two pure resolution functions: `ResolveParallaxPosition(element BGElement, cameraX, cameraY float64) (x, y float64)` implementing `x = StartX + cameraX*DeltaX` (and the `y` equivalent) per the documented convention, and `ResolveAnimationFrame(anim BGAnimation, elapsedTicks int) SpriteRef` walking the frame sequence (respecting `LoopStart` the same way `air.Animation` does) and returning a blank sentinel (`SpriteRef{-1,-1}`, mirroring `air.Frame.IsBlank()`'s convention) for an empty sequence, an out-of-range `LoopStart`, or a sequence whose total duration is zero or negative, instead of panicking or indexing out of bounds. Parsing `[Begin Action N]` blocks into `BGAnimation` from real `.def` text is explicitly **not** done here — `Parse`/`BGElement` are left unchanged beyond these two additions, and a follow-up backlog item is filed for that wiring.

**Reason:** Splitting "resolution logic" from "parser wiring" mirrors the exact order `character`'s own `air`/`cns` packages were built in (data model and pure functions first, parser support catching up in a later item), keeping this item's scope matched to its own acceptance criteria, which only asks for the computations, not new `.def` parsing. Reusing the `air` package's `Animation`/`Frame`/`LoopStart`/blank-sentinel shape avoids inventing a second convention for what is, per Elecbyte's docs, the identical underlying file syntax.

**Rejected alternatives:**
- *Add `Frames`/`LoopStart` directly onto `BGElement`* — rejected: `BGElement` is already wired through `Parse`/`Serialize`; adding fields no writer path populates or reads yet would leave dead, untested surface on an otherwise-complete type. A separate `BGAnimation` type stays honest about what is and isn't wired up.
- *Implement `[Begin Action N]` parsing now, as part of this item* — rejected: not asked for by the acceptance criteria, and a large enough addition (new section grammar, `.air`-syntax frame-line parsing reused or duplicated) to deserve its own item and its own test/compat pass, consistent with how `character`'s own read-path items were sequenced.
- *`screenX = start - camera*delta`* — considered (would match a "world-fixed element scrolls opposite the camera pan" mental model) but rejected: contradicts the plain wording of MUGEN's own documented `delta` definition, which this decision follows literally instead of a physically-derived guess.
