## Project overview

OpenKakutou `stage` is a read/write Go library for MUGEN/Ikemen GO stage (background) `.def` files: BGdef, BG elements/layers, camera bounds, stage boundaries, and parallax/animated backgrounds. It depends on the sibling [`sff`](https://github.com/openkakutou/sff) repo for stage sprite sheets, never on `character`. It has no rendering dependency and must compile cleanly to WebAssembly. It is consumed by `stage-viewer-web` (read-only visualization) and `stage-editor` (read+write). See the roadmap's `.vibe/decisions/009-scope-stage-parser-library-lifebar-no-library.md`.

**Stack:** Go 1.26, compiled to WASM (`GOOS=js GOARCH=wasm`) for web consumers. No UI code lives in this repo.
**Type:** library

## Project context <!-- keep -->

Long-term scope of the OpenKakutou org (github.com/openkakutou), stage domain:
- `stage` (this repo) — read/write library for MUGEN/Ikemen GO stage (background) files
- `stage-viewer-web` — visualize a stage: layers, parallax, animated backgrounds, via this repo's WASM build. Read-only.
- `stage-editor` — modify and/or create a stage: read+write UI on top of this repo.

This repo follows the same shape `character` established for its own domain: data model before parser, format-preserving round-trip serialization, a WASM entrypoint, and fixture-driven compatibility testing against real files. It depends on `sff` (a shared, domain-independent repo, see `.vibe/decisions/007` in the roadmap) for sprite sheet decoding — never duplicates `.sff` parsing, and never depends on `character` for it.

## Scope of this repo <!-- keep -->

Read **and** write support for MUGEN/Ikemen GO stage (background) `.def` files:
- Stage data model — `BGdef`, BG elements/layers, camera bounds, stage boundaries
- `.def` parsing — text-format parser, MUGEN + Ikemen GO compatible
- `.def` serialization — format-preserving round trip, same guarantee `character` provides for its own `.def`/`.air`/`.cns`
- Sprite integration via `sff` — resolving BG element sprite references against `.sff` sprite sheets
- BG element frame/animation resolution — parallax scroll deltas and animated background playback state

## Design constraints <!-- keep -->

1. **No rendering dependency.** This module only parses/serializes data — no OpenGL, no canvas, nothing rendering-related. It must compile cleanly to WASM, and be usable as-is by both `stage-viewer-web` and `stage-editor`.

2. **Read and write live in the same repo, but as clearly separated sub-concerns** (not necessarily separate packages from day one — separate the concerns internally):
   - **Read path**: exposes a minimal, stable, pure-data API.
   - **Write path**: needs to preserve as much of the original file structure as possible on round-trip (ordering, comments) for `.def` — otherwise every save from `stage-editor` produces a huge, unreadable Git diff, which hurts community collaboration on stage files.

3. **Depends on `sff`, never on `character`.** Stage BG elements reference sprite sheets in the `.sff` format; sprite decoding belongs to the shared `sff` repo, not to this one or to `character`. See the roadmap's decision `007`.

## Development workflow (Vibe Coding)

The user is the **Product Owner only**. They describe requirements and evaluate outcomes — they do NOT write or manually test code.

### Definition of Done

A task is complete ONLY when ALL of the following are true:

- [ ] Implementation code is written
- [ ] Tests covering the nominal path exist and pass
- [ ] Tests covering edge cases and error paths exist and pass
- [ ] Lint exits with code 0 — `gofmt -l .` reports no files, `go vet ./...` is clean
- [ ] All tests pass — `go test ./...`
- [ ] No debug artifacts left in code (`fmt.Println` debug calls, commented-out code, etc.)

**Never present a result to the user if tests are failing.**

### TDD workflow

For every feature or fix:

1. **Write tests first** — describe expected behavior through tests before writing implementation
2. **Confirm tests fail** — run `go test ./...` and verify new tests fail (red)
3. **Write implementation** — minimum code to make tests pass
4. **Confirm tests pass** — run `go test ./...` and verify all tests pass (green)
5. **Refactor if needed** — clean up while keeping tests green
6. **Run lint** — run `gofmt -l .` and `go vet ./...`, fix any issues
7. **Present result** — summarize what was done, what was tested, and the test output

### Bug fix workflow

1. **Reproduce in a test first** — write a failing test that captures the bug
2. Fix the bug
3. Confirm the test passes
4. Present result with the test name that now covers the bug

### Self-correction loop

If tests or lint fail:
- Do NOT ask the user for help
- Diagnose the failure, fix it, re-run
- Repeat until green (max 3 self-correction attempts)
- Only escalate to the user if the failure reveals an ambiguous requirement

## Testing conventions

- Test location: co-located with source, `*_test.go` per package (e.g. `version_test.go` alongside `version.go`)
- Test runner: built-in `go test`
- One test file per source file
- Test names must describe behavior: `TestParseStage_ReturnsError_OnMissingBGdefSection`, not `TestParse`
- Always cover: happy path + at least 2 edge cases + error/invalid input
- Round-trip tests are required for any write-path code (`.def`): parse → serialize → byte-for-byte (or semantically) identical output

## Constraints

- Never leave dead code or unused imports
- Never hardcode secrets — use environment variables
- Never skip tests to meet a deadline — fix the code instead
- Style is enforced by tooling, not by convention — always run `gofmt -l .` and `go vet ./...` before presenting results
- No rendering dependency, ever — see the design constraints above
- Depend on `sff` for sprite sheet handling — never reimplement `.sff` parsing here, never depend on `character`
- Never hardcode a local, machine-specific fixture corpus path into source, tests, or committed config (see `.vibe/fixture-sources.md` once item 007 lands, mirroring `character`'s own convention)
