# WebAssembly entrypoint

`cmd/wasm` builds the library into a WebAssembly module a browser (or any
JS host) can load directly — no local Go toolchain needed. It is thin glue
only: all real logic lives in the root `stage` package (see
[docs/api.md](api.md)), which is unit-tested independently of this file.

## Building locally

```sh
GOOS=js GOARCH=wasm go build -o stage.wasm ./cmd/wasm
cp "$(go env GOROOT)/lib/wasm/wasm_exec.js" .
```

`cmd/wasm/main.go` is build-tag gated (`//go:build js && wasm`), so it is
invisible to a normal host build/test — `go build ./...` and `go test ./...`
never touch it.

## JS API

The module registers a single global on `js.Global()` with two functions.

### Loading a stage

```js
globalThis.OpenKakutouStage.load(defBytes)
```

- **Arguments**: one `Uint8Array` — the raw bytes of a stage's `.def`
  file, already fetched or selected by the caller. The module never
  touches a filesystem itself; the caller supplies the buffer directly.
- **Return value**: always a plain object `{ stage, error }`, exactly one
  field non-`null`:
  - `stage` — a JSON string of the loaded `Stage` (see
    [docs/data-model.md](data-model.md) for the Go shape; every field uses
    an explicit `json:"..."` tag).
  - `error` — a descriptive, line-numbered message naming what failed to
    parse, or the reason the call itself was malformed (e.g. a wrong
    argument count).
- The function never throws: an internal panic is recovered at this
  boundary and reported as `error` instead of crashing the whole page's
  WASM instance. A prior error does not leave the module in a broken
  state — the next call is handled independently.

#### Example

```js
const result = globalThis.OpenKakutouStage.load(defBytes);
if (result.error) {
  throw new Error(result.error);
}
const stage = JSON.parse(result.stage);
```

### Saving an edited stage

```js
globalThis.OpenKakutouStage.save(originalDefBytes, editedStageJSON)
```

- **Arguments**: `originalDefBytes` — a `Uint8Array` of the `.def` file's
  own previously loaded bytes (an empty array for a brand new stage with
  no original file yet); `editedStageJSON` — a JSON string matching
  `load`'s own `stage` shape, the caller's current in-memory
  representation, edited or not.
- **Return value**: always a plain object `{ bytes, error }`, exactly one
  field non-`null`:
  - `bytes` — a `Uint8Array` of the serialized `.def` file. Byte-exact to
    `originalDefBytes` when the model describes no real change (down to
    treating an empty `elements` list the same whether it arrived as
    `null` or `[]`); freshly generated, valid, re-loadable text otherwise,
    which does not preserve the original's comments/ordering.
  - `error` — a descriptive message: a malformed original, malformed
    JSON, or a wrong argument count.
- Same never-throws, never-broken-after-an-error guarantee as `load`.

See [docs/api.md](api.md#serializedef) for the underlying
`stage.SerializeDef` function this glue calls, and
[`.vibe/decisions/005-wasm-entrypoint-mirrors-character-load-save-shape.md`](../.vibe/decisions/005-wasm-entrypoint-mirrors-character-load-save-shape.md)
for why the API is shaped this way (mirroring the sibling `character`
repo's own WASM entrypoint).

#### Example

```js
const edited = JSON.parse(loadResult.stage);
edited.bgDef.zOffset = 200;

const saveResult = globalThis.OpenKakutouStage.save(defBytes, JSON.stringify(edited));
if (saveResult.error) {
  throw new Error(saveResult.error);
}
// saveResult.bytes is ready to offer as a browser download
```

## Not yet exposed

Resolving a sprite reference to actual pixel data (`SpriteResolver`, see
[docs/api.md](api.md#spriteresolver)) is not exposed through this
WASM entrypoint yet — only the `Stage` data model's sprite *references*
(`group`/`image` pairs) travel through `load`'s JSON. A consumer needing
real pixels currently has no WASM-side path for that; see the sibling
`character` repo's own `resolveSprites` global for the shape this would
likely mirror once added.

## Verifying a build

`cmd/wasm/smoke.mjs` is a Node.js harness that loads a built module the
same way a browser would (via `wasm_exec.js`) and exercises both the
nominal path and error paths for `load` and `save` — the closest thing to
`go test` this file has, since `syscall/js` code cannot run under the
plain Go toolchain:

```sh
node cmd/wasm/smoke.mjs [path/to/stage.wasm]  # defaults to ./stage.wasm
```

## Release pipeline

`.github/workflows/release.yml` runs on every pushed tag matching
`v[0-9]*.[0-9]*.[0-9]*` (e.g. `v1.2.3`). It builds and tests the module
normally first (`go build ./...`, `go test ./...`, `go vet ./...`) —
nothing is published if any of those fail — then builds `stage.wasm` and
copies the matching `wasm_exec.js` (failing the build loudly if that file
isn't found at its expected path, rather than silently publishing a stale
or missing asset), publishing both as assets on that tag's GitHub Release
under stable, predictable names. `wasm_exec.js` is Go-version-specific
glue; the workflow always builds and copies it from the same Go toolchain
install that produced the `.wasm`, so the two published files are
guaranteed to be a matched pair — a consumer should always fetch both from
the same release, never mix versions.
